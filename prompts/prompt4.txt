## Chunk model

Each generated chunk should preserve metadata.

At minimum:

{
    "chunk_id": "...",
    "document_id": "...",
    "page_number": 1,
    "chunk_index": 0,
    "text": "..."
}

If a chunk spans multiple pages, design the metadata carefully so the source page information is not lost.

For this first implementation, prefer keeping chunks within a single page if practical.

Explain this design decision.

## Configurable chunking

Do NOT hard-code chunk size and overlap directly inside the chunking function.

Create configuration values such as:

chunk_size = 500

Use a clean configuration approach consistent with the existing project.

The chunking service should receive the configuration rather than depending on random constants throughout the code.

## Chunking behavior

Implement a basic character-based chunking algorithm first.

Do not introduce LangChain or another chunking framework.

The algorithm should:

1. Receive page-level text.
2. Normalize unnecessary whitespace.
3. Split text into chunks based on chunk size.
4. Apply chunk overlap.
5. Preserve page number.
6. Generate a unique chunk ID.
7. Generate a chunk index.
8. Avoid empty chunks.
9. Handle pages shorter than the chunk size.
10. Handle pages with no extractable text.

Explain the algorithm clearly.

For example, if:

chunk_size = 500
chunk_overlap = 50

then conceptually:

Chunk 1:
characters 0–499

Chunk 2:
characters 450–949

Chunk 3:
characters 900–1399

Do not blindly copy this example if your implementation uses a better boundary strategy, but keep the implementation simple.

## Important design consideration

We will later experiment with different chunk sizes and overlaps.

Therefore the chunking implementation must make it easy to change:

- chunk size
- overlap

without changing the core chunking code.
